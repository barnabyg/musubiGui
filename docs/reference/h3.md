# MiniMax H3 T2VA LoRA

The initial recipe uses **guidance loss**, not plain flow matching. Every cache/train/sample
stage uses task `t2va` with the released FL2VA base. Guidance loss works with the installed
prequantized ConvRot INT8 transformer and needs an unconditional text cache, generated with
`--uncond_output`. Training passes `--h3_guidance_loss_scale 4`, sigma minimum 0.15 and that
cache. Both video and audio losses remain enabled; no `--video_only` is used for a job with
videos. Job images use [upstream's one-frame recipe](#image-and-mixed-trials-1-november-2026):
`--one_frame` on both caches and training, plus `--video_only` when a job has only images.

Settings component keys and the actual artifacts tested:

| Key            | Artifact                                           |
| -------------- | -------------------------------------------------- |
| `h3_dit`       | `minimax_h3_fl2va_pruned_int8_convrot.safetensors` |
| `h3_text`      | `qwen3vl_32b_minimax_h3_nvfp4_awq.safetensors`     |
| `h3_video_vae` | `minimax_h3_video_vae_fp16.safetensors`            |
| `h3_audio_vae` | `minimax_h3_audio_vae_fp32.safetensors`            |

These four existing artifacts total 42,470,585,471 bytes (~42.5 GB); model payloads stay outside
Git. H3 supports BF16/ConvRot INT8 transformer inputs and BF16/ConvRot INT8/NVFP4+AWQ text
encoders. FP8 artifacts and NVFP4 transformers are unsupported. NVFP4 text **block scales**
can legitimately be stored as FP8; they are not FP8 model weights. The audio VAE is mandatory
even if a dataset has no supervised audio. The official H3 processor/config/tokenizer are
downloaded into each run's isolated HF cache; generic Qwen tokenizer files are not equivalent.

Training-adapter merging requires BF16 source weights and cannot merge into the installed
prequantized INT8 base. Teacher matching adds teacher-specific tasks and a privileged forward.
Guidance loss avoids those extra artifacts/task distinctions for this first T2VA fixture.
These alternatives are source-evaluated, not experimentally qualified by this work.

The fixed smoke geometry is 256×256, 124 frames at 24 fps, rank/alpha 4, batch one and two
steps. H3 requires spatial multiples of 32 and frame counts `17*n+5` in the released 124–345
range. Effective batch size should use gradient accumulation; dataset batch size stays one.
Text caching uses 50 swapped blocks. Training uses BF16, SDPA, 48 swapped blocks, gradient
checkpointing, **`--block_swap_h2d_only`**, AdamW and loader workers zero. Sampling uses four
steps, no CFG/negative prompt controls, and runtime application of the saved LoRA.

The expected outputs are `checkpoints/h3-reference.safetensors` and `samples/sample.mp4`.
Run the one command from the reference README; the CLI prepares aligned synthetic video and
same-stem WAV and confirms `supervised_audio_fraction=1.000000` before training. The sample
must decode both video and audio. Missing audio, silence placeholders, unsupported conditioning
modes and off-spec geometry are not claimed as tested training workflows.

## Actual target-PC observations, 26 October 2026

The [full scenario](evidence/h3-success.json) passed on Windows 11, RTX 3090 (24 GiB), driver 621.01, Python
3.12.10, PyTorch 2.13.0+cu130 / CUDA 13.0, musubi-tuner 0.3.6 at the pinned revision.
Actual host RAM was **95.6 GiB**. A 64 GB restriction in older evidence no longer applies;
this scenario establishes execution on the target machine.

| Stage         | Seconds | Peak process-tree RSS (GiB) | Peak device VRAM (GiB) |
| ------------- | ------: | --------------------------: | ---------------------: |
| Fixture       |   0.563 |                       0.006 |                   1.12 |
| Latent cache  |   9.453 |                        1.29 |                   7.08 |
| Text cache    |  18.906 |                       29.36 |                   4.46 |
| Training      |  50.844 |                       20.44 |                  10.65 |
| Generation    |  51.984 |                       34.32 |                   6.86 |
| Sample decode |   0.563 |                       0.006 |                   1.10 |

Measurements are sampled and whole-device VRAM includes unrelated baseline allocation.
The sampled run used approximately 1.14 GB of additional disk according to free-space
deltas; this includes unrelated activity and is not a storage sizing guarantee. Two-step
checkpoints and temporary compiler/HF caches are included; 42.5 GB source weights are not.
See the committed evidence and common measurement limits before interpreting these numbers.

The final MP4 decoded 124 video frames and 165,888 audio samples. Edge playback reported
5.167 seconds, 256×256, increasing playback time and 28,044 decoded audio bytes with no media
error. Playback was muted during automation; audible quality and training usefulness have
not been human-reviewed. Two steps and a four-step sample are execution evidence only.

The [first complete attempt](evidence/h3-classic-swap-failure.json) cached successfully but failed at training step zero with
`MiniMax-H3 block 0 parameter attn.qkv_proj.weight is on cpu, expected cuda after wait`.
Guidance loss performs a no-gradient forward followed by another forward before backward;
classic swapping did not reload block zero for that restart. A [single-variable trial](evidence/h3-h2d-trial.json) using
H2D-only swapping completed both steps and saved its final checkpoint. The complete scenario
then passed with that setting. No upstream code or dependencies were changed. Further no-swap
trials were unnecessary once the supported alternative worked.

## Production-size trial, 29 October 2026

[Issue #26](https://github.com/barnabyg/musubiGui/issues/26) ran the GUI recipe at
larger geometry on the same host. The dataset was 20 owner-provided talking clips,
6 s at 30 fps, each with supervised speech audio. Every run used 124 frames, head
extraction, rank/alpha 8, 48 of the model's 50 blocks streamed with H2D-only
swapping, and gradient checkpointing. The GPU power limit was 245 W. The
[evidence file](evidence/production-trial.json) records each attempt.

| Size    | Result                                                               | Step time |
| ------- | -------------------------------------------------------------------- | --------- |
| 832×480 | CUDA out of memory at step 0: 17.7 GiB allocated, 5.5 GiB fragmented | —         |
| 640×352 | Trains; 21.7 GiB peak device VRAM; 10, 20 and 30-step runs completed | 70–72 s   |

At 832×480 nothing else can help on this PC: upstream allows no more swapped blocks,
124 frames is the minimum, and `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`
is unsupported by PyTorch on Windows. Sizes between 640×352 and 832×480 are untested.
Job review accepts 0–48 swapped blocks. 49 cannot train on the pinned upstream:
[issue #42](https://github.com/barnabyg/musubiGui/issues/42) tried it at 640×352 on
30 October 2026 (run `b44f5f27`, 280 W), and training exited 1 during argument
validation, before any model loaded, with `ValueError: --blocks_to_swap for MiniMax-H3
must be <= 48` ([evidence](evidence/block-swap-qualification.json)). A higher limit
would need an upstream change.

At 640×352 the latent cache took 7 minutes for 20 clips (7.2 GiB peak VRAM), the
text cache 40 seconds, and a 10-step sample 3.3 minutes including load
(9.9 s per inference step, 32.1 GiB peak RSS, 49.9 GiB host RAM). The sample decoded
124 frames at 24 fps with 5.18 s of 32 kHz stereo AAC; its audio envelope is
speech-like but was not listened to. Each rank-8 LoRA is 149,165,288 bytes and each
state folder about 427 MiB.

Restore as new segment was checked here: a 20-step run saved state at 10 and 20, and
restoring the step-10 state for 10 more steps resumed the optimizer and scheduler
(the segment's saved state reports step 20) while upstream reset its displayed
counter and data position. This is the Measured H3 preset. Useful learning, audio
quality and the block-count help text (#36) remain open.

## Image and mixed trials, 1 November 2026

[Issue #105](https://github.com/barnabyg/musubiGui/issues/105) ran the guidance-loss recipe with
upstream's one-frame image mode through the upstream CLI, at 640×352, rank 8 and the 280 W limit
([evidence](evidence/combined-image-video-trial.json)). Both runs used six images of varied
shapes. `--one_frame` was added to the latent cache, text cache and training.

| Run                                                       | Steps | Result | Image step | Video step | Peak training VRAM |
| --------------------------------------------------------- | ----: | ------ | ---------: | ---------: | -----------------: |
| Image-only, also `--video_only` on training               |    10 | Passed |       ~5 s |          — |           5.98 GiB |
| Mixed, one image and one video section, no `--video_only` |    16 | Passed |       ~5 s |      ~78 s |          22.25 GiB |

The mixed run's four 30 fps clips had embedded speech audio. Its image and video sections shared
the TOML but not a cache directory, as upstream requires. Upstream reported 100% audio supervision
for the clips and treated each image's audio as a silent placeholder excluded from supervision. It
printed no audio warning, only the note that image-only runs should pass `--video_only`. Each image's
latent cache is 85,980 bytes, including its two silent audio frames, and the disk estimate's
image formula was corrected to match. Both 10-step samples decoded 124 frames and 165,888 audio
samples. They were not watched or listened to.

Those CLI runs read the clips from a `video_directory`. A further 12-step mixed run through the
application used what it emits, a `video_jsonl_file` beside the `image_directory`, and also passed:
about 6 s per image step, about 75 s per video step and the same 22.25 GiB peak.

**Qualified:** image-only and mixed H3 training run to completion on this PC with this recipe, so
[job review accepts H3 images](../jobs.md#h3-images), with a warning. **Not qualified:** learning from images, and whether a LoRA trained on
images is useful for video. Upstream calls one-frame mode experimental, says mixed training is
expected to work but is untested, and says image-trained LoRAs applied to video are unvalidated.
These short runs change none of that: they prove mechanics only, and showing learning needs 600+
steps and human review. Bucketing and other sizes were not tried.
